Codex CLI→LiteLLM→OpenAI

One config file, shipped once, for every engineer.

A self-hosted gateway for the Codex CLI. Docker Compose brings up LiteLLM, setup mints a virtual key, rewrites ~/.codex/config.toml to point at it, and ends by sending a real request through the whole path. Hand the repo to your coding agent, or run the one script yourself.

$ git clone https://github.com/misbahsy/codex-litellm-stack $ cd codex-litellm-stack $ ./scripts/setup.sh
Needs Docker running and an OpenAI API key.

Set it up

An agent can look at the machine before it changes anything: whether Docker is running, what already owns port 4000, whether the ~/.codex/config.toml it is about to overwrite is one you want to keep. Paste this into Codex from an empty directory and it takes the repo from there.

Clone https://github.com/misbahsy/codex-litellm-stack, cd
into it, and set it up so my Codex CLI goes through the LiteLLM
gateway instead of calling OpenAI directly. Read AGENTS.md and

Codex reads AGENTS.md natively, and it discovers skills under ~/.codex/skills, so the three in .codex/skills/ work where they sit or copied there. They carry the actual procedures, so the agent follows a written method instead of improvising over your dotfiles:

SkillWhat it covers
codex-litellm-setuppreflight, run setup, verify with a real turn, report what changed outside the repo
codex-litellm-troubleshootread the doctor output, fix failures in dependency order, and the failures the doctor can’t see
codex-litellm-fleetthe MDM artifact, the secret scan it must pass, per-user keys and budgets

The skills orchestrate the scripts rather than replacing them, so the manual tab is the same sequence with you at the keyboard.

Six steps, no agent. Everything stays inside the repo except ~/.codex/config.toml and, on macOS, one LaunchAgent.

  1. Clone the repo

    $ git clone https://github.com/misbahsy/codex-litellm-stack $ cd codex-litellm-stack

    Every command below runs from that directory.

  2. Start Docker

    $ docker info

    If that prints an error, Docker is installed but not running. Open Docker Desktop and wait for it to finish starting.

  3. Check that port 4000 is free

    $ lsof -nP -iTCP:4000 -sTCP:LISTEN

    No output means nothing holds it. If a tunnel or dev server does, add --port 4010 to the next step: whatever is on that port will answer the health check and the checks will pass against the wrong server.

  4. Run setup

    $ ./scripts/setup.sh # --port 4010 bind somewhere else # --no-desktop CLI only, skip the LaunchAgent # --enterprise also write dist/config.toml for MDM

    It asks for your OpenAI API key and saves it to docker-compose/litellm.env at mode 600. Then it starts LiteLLM and Postgres, mints a virtual key against the gateway, writes ~/.codex/config.toml after backing up any existing one, and on macOS installs the LaunchAgent that hands the key to the desktop app.

    Three keys, three jobs. Your OpenAI key stays in the gateway and never leaves the machine running it. The master key setup generates is the admin credential: it logs into the LiteLLM UI and issues keys. The virtual key is the one your Codex client gets, scoped so you can budget or revoke it on its own. Setting this up for yourself, you hold all three. Running it for a team, one admin does this once and issues a virtual key per person from the UI.

  5. Start Codex

    $ ./dist/start-codex.sh # CLI, key already exported $ codex app # desktop app; quit and reopen it once

    dist/start-codex.sh is generated and holds a live key, so dist/ is gitignored. export LITELLM_API_KEY=… && codex does the same thing.

  6. Confirm the requests go through the gateway

    $ ./scripts/doctor.sh $ codex exec "reply with the word CONNECTED and nothing else" $ docker compose -f docker-compose/docker-compose.yml logs litellm --tail 20

    The doctor runs five checks along the request path. The log line from that last command is what tells you Codex went to your gateway rather than straight to OpenAI.

[keys]three keys,
three jobs

One OpenAI key in, one key per person out

Your OpenAI key is written once, into docker-compose/litellm.env on the machine running the gateway. Nothing else on the network sees it. Setup then uses the master key to mint a virtual key, and that is the credential Codex sends.

KeyLives inWhat it does
OPENAI_API_KEYdocker-compose/litellm.env, chmod 600pays OpenAI; the gateway is the only thing that reads it
LITELLM_MASTER_KEYthe same env fileadmin: signs into /ui, issues and revokes virtual keys
virtual keydist/start-codex.sh and the LaunchAgentwhat Codex sends on every request; budget or revoke it alone

Working solo, you will use one virtual key and never think about it again. On a team, one key per person is what makes the spend view and the revoke button mean anything.

[models]docker-compose/
litellm-config.yaml

Real model names, straight through

The only thing that changes is where requests go. There’s no alias layer to learn and nothing gets renamed. A model id you would send to OpenAI works unchanged through the gateway, so people keep picking models the way they already do.

how you choose, unchanged
# whatever `model` is set to in config.toml
codex

# any model the gateway serves, ad hoc
codex -m gpt-6-astra

# a saved model + reasoning-effort pair
codex --profile deep

litellm-config.yaml lists the models you want visible in /v1/models, which is also where per-model rate limits and budgets attach, plus a "*" catch-all so anything else passes through without an edit. Delete that entry and the gateway serves only the list, which is how you restrict a fleet to approved models from one file.

[client]~/.codex/
config.toml

Written for you, with the timeouts a coding agent needs

Codex holds a streaming connection open for the length of a whole turn, so the defaults are wrong for it out of the box. The generated file sets a two-hour idle timeout and speaks the Responses wire protocol, which LiteLLM serves directly.

~/.codex/config.toml
# generated by scripts/setup.sh; only base_url is really new
model = "gpt-5.6-terra"
model_provider = "litellm"
model_reasoning_effort = "medium"

[model_providers.litellm]
base_url = "http://localhost:4000/v1"
env_key = "LITELLM_API_KEY"
wire_api = "responses"
stream_idle_timeout_ms = 7200000   # two hours; a turn can take that long
stream_max_retries = 5

[profiles.astra]
model = "gpt-6-astra"
model_reasoning_effort = "high"

The key in LITELLM_API_KEY is a virtual key minted at setup. Budget it, rate-limit it, or revoke it from the LiteLLM UI. The gateway master key never reaches a laptop.

[desktop]~/Library/
LaunchAgents

The desktop app, working from the first launch

codex app and the icon in your Dock read the same config file, so they reach the gateway too. The key is the part that needs help. macOS gives an app launched from Finder, the Dock or Spotlight the environment of your GUI login session, never a shell’s, so a key exported in .zshrc or by a launcher script is invisible to it.

Setup installs a LaunchAgent that puts the key into that session at every login, so it survives a reboot and there is no per-launch command to remember.

installed once by scripts/setup.sh
# ~/Library/LaunchAgents/com.codex-litellm-stack.env.plist
launchctl setenv LITELLM_API_KEY sk-…   # RunAtLoad, every login

# confirm the app will find it
launchctl getenv LITELLM_API_KEY

# CLI only, if you'd rather not
./scripts/setup.sh --no-desktop

The plist holds the key at chmod 600, and the login session makes it readable to every process you run, which is a wider reach than the CLI-only path. What sits there is a budgeted virtual key you can revoke from the LiteLLM UI, not the OpenAI key. scripts/uninstall-desktop-env.sh takes it back out.

[verify]scripts/
doctor.sh

Five checks along the real request path

Setup finishes by running the doctor, and you can run it again any time. It sends an actual request through /v1/responses and then a second one with streaming on, because a gateway that answers a health check can still fail the kind of request Codex actually sends.

$ ./scripts/doctor.sh
1  gateway reachable        http://localhost:4000        ok
2  key accepted             /v1/models → 200             ok
3  model published          gpt-5.6-terra                 ok
4  provider round trip      /v1/responses → PONG         ok
5  streaming                12 SSE frames                ok

client  base_url matches gateway                       ok
        wire_api = "responses"                         ok
        LITELLM_API_KEY exported                       ok

desktop GUI session carries the same key                ok

When a check fails it names the cause rather than the symptom:

4 provider round trip: HTTP 401 OpenAI rejected the key. Check OPENAI_API_KEY in docker-compose/litellm.env.
1 gateway reachable: wrong server Something is listening on :4000, but it is not LiteLLM. Free the port or use --port.
[fleet]setup.sh
--enterprise

The same file, pushed to every machine

Run setup with --enterprise and it also writes a secret-free dist/config.toml: base URL, wire protocol, timeouts and profiles, with the credential left as an environment variable for your own secret delivery. The codex-litellm-fleet skill has the grep that proves it carries no secret. That file is what goes out over MDM.

Engineers install Codex, get the config from device management, and the first codex they run is already pointed at the gateway.
